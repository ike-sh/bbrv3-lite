## 1. 真实生产 Bug 与精确根因

用户报告的环境为 Debian 13、6.12.96+deb13-amd64、amd64/x86-64-v3、967 MiB、KVM；程序 v8.0.8，当前 bbr / fq，persistence enabled / SYNCED。上述为用户提供的当前状态，本轮未 SSH 重查或改动，不用早先不同时间的生产状态替代它。

用户从“XanMod 内核管理 → 安装 LTS”确认后，收到“缺少命令: gpg / exit 1”。已独立读取正式基线的真实代码，定位到 [v8.0.8 kernel.sh:102](https://github.com/ike-sh/bbrv3-lite/blob/4b9bb71d5b797dcf115863fbcb27b7fd4350f17e/src/kernel.sh#L102)：

```bash
require_commands apt-get apt-cache curl gpg || return 1
# ...
apt-get update -qq
DEBIAN_FRONTEND=noninteractive apt-get install -y ca-certificates curl gnupg
```

`gpg` 是下一步 gnupg 安装的产物，却在第 102 行被当作前提；缺少时第 105 行不可达。curl 缺失同理。根因是 **bootstrap 依赖顺序错误**，并非 CPU level、LTS 候选或 BBR/FQ 配置问题。

调用链为 cli.sh kernel_menu → submenu_run/menu_run → kernel_install lts。原 104/108/111/119/123 行等未显式处理 APT、下载、转换与安装失败；菜单/条件调用场景不能仅依靠 errexit 防止继续执行。因此没有只删除 require_commands 中的两个名称，而是对各阶段补充显式失败传播。

`case_legacy_order` 使用基线 102–105 行的原顺序，在缺少 gpg、有 curl 的 fixture 中实际证明：返回失败，APT update 和 install 均未开始。新流程在相同缺失条件下成功进入依赖安装；真实 Debian 13 both-missing 场景进一步完成了实际安装。

## 3. 新 bootstrap 执行顺序

入口仍为 [kernel_install:221](../src/kernel.sh#L221)，无新 CLI 参数：

1. root 与产品全局 flock 保持原样；检查 track、Debian/Ubuntu、amd64、容器及既有 Secure Boot 限制。
2. 仅把 apt-get、apt-cache、dpkg-query 视为基础能力；检查合法 codename，拒绝源行注入。
3. [kernel_bootstrap_dependencies:89](../src/kernel.sh#L89) 用严格错误模式更新已有 APT 索引，任一源更新失败均停止。
4. 按 dpkg 安装状态和实际 curl/gpg 可用性，计算缺失的 ca-certificates、curl、gnupg；已具备时不重复安装。
5. 对完整缺失包集合运行 APT simulation / network guard，再以 --no-remove 安装。
6. 实际 require_commands curl gpg；APT 声称成功但命令仍缺失时停止，不能进入 key 下载。
7. 建立本次临时目录与独立 GNUPGHOME，下载官方 HTTPS 公钥；只允许 HTTPS 和 HTTPS redirect。
8. 解析公钥、执行 dearmor、再次解析转换结果；这些都成功后才处理正式 keyring/source。
9. 先核对两个已有目标；完全一致则复用，不同或非普通文件则保留并停止。缺失文件用同目录临时文件加硬链接无覆盖原子创建，权限 0644。
10. 以专用 signed-by keyring 进行正常 APT repository update/签名验证；失败停止并清理本次新建、仍归本次所有的文件。
11. 原 CPU 等级/track candidate 选择 → 内核包 simulation/guard → --no-remove 实际安装 → 如有 update-grub 则检查其结果。
12. 明确报告“内核包已安装，当前运行内核未切换/未删除，维护窗口自行重启并 kernel status 验证”；不自动重启或重配 TCP/qdisc。

bootstrap 成功和内核包安装成功分别输出，不把“依赖已就绪”写成“XanMod 已安装”。

## 4. APT 安全保护及失败处理

[apt_network_guard:75](../src/kernel.sh#L75) 现在接受多包 argv，以 `LC_ALL=C apt-get -s install ...` 检查下列六类 Remv，支持 :amd64 等限定名：

```text
openssh-server
systemd
systemd-resolved
iproute2
network-manager
ifupdown
```

依赖安装和内核安装均执行该 guard。模拟异常保留 APT 原始错误；关键组件移除在实际 install 前拒绝。实际安装另加 --no-remove，即使 simulation 后状态变化，也不允许 solver 自动删除包或正在运行的内核。APT 文档明确该选项在存在移除计划时中止；严格 update 失败模式也由 APT 支持。[Debian apt-get 手册](https://manpages.debian.org/trixie/apt/apt-get.8.en.html)

APT update、包冲突、依赖安装、磁盘不足、key 下载/转换、repo 更新、内核安装及 GRUB 更新都显式检查返回值。stderr 不被通用成功提示替换；条件调用 fixture 强制验证不会越过失败进入下阶段。不使用 force-yes、allow-unauthenticated、trusted=yes 或关闭签名检查。

仓库阶段单独 subshell/EXIT-HUP-INT-TERM cleanup，调用者原有 EXIT/rollback trap 与锁不被改写。失败只移除本次新建且 **设备/inode 与内容均仍匹配** 的 keyring/source；已有文件不覆盖、不备份，也不删除。临时文件删除失败明确返回非零并报告路径，不能把清理失败掩盖为完整成功。

已经成功安装的 bootstrap 包和 APT 自己的缓存不被自动卸载/清空，APT 已完成的包事务也不被声称已回滚。产品原有恢复/可信 baseline 功能保持原样；没有额外长期安装备份或系统快照。

## 5. GPG 与配置安全

- 来源固定为官网公布的 `https://dl.xanmod.org/archive.key`，curl 强制 HTTPS，包括 redirect；没有改用未知镜像或禁用 TLS 验证。[XanMod 官方安装说明](https://xanmod.org/)
- gpg 使用 --no-options、独立临时 homedir、--batch、机器可解析 --with-colons / --show-keys；必须出现 public key 记录，拒绝非 key/secret 数据。
- dearmor 只写临时文件，失败不发布；转换结果再校验，避免空文件或损坏数据进入 keyring。GPG 官方文档支持该机器可解析格式。[GnuPG 文档](https://www.gnupg.org/documentation/manuals/gnupg/GPG-Input-and-Output.html)
- **没有实现指纹 pin，也没有编造“官方指纹”或把运行时读出的 fingerprint 冒充独立信任锚。** 信任入口为官网 HTTPS key 分发；随后由 APT 的 signed-by、InRelease 和包 hash 验证建立仓库/包信任链，真实 APT 已执行。
- 保留官方现有 `http://deb.xanmod.org CODENAME main` 源格式以兼容 v8.0.8 配置；HTTP 不替代签名验证。main 是 APT component，和用户选择的 Main/LTS 内核轨道不同。
- 两个正式路径仍为 /etc/apt/keyrings/xanmod-archive-keyring.gpg 与 /etc/apt/sources.list.d/xanmod-release.list。两者先一起核对兼容，再分别无覆盖原子发布；不存在旧配置备份。
- 对人工修改、额外条目或不同 key 的既有配置采取保留并停止的策略；不自动迁移/旋转 key。必要时需用户审查差异，不能为了安装而覆盖有效原配置。

## 6. LTS/Main、内核与当前网络兼容性
