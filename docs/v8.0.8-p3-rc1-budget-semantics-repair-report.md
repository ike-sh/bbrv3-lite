## 1. Root cause and call chain

旧构建在 `measurement_budget_feasibility_gate` 中正确发现：已用 2562106393 bytes、仍有 3880344551 bytes、expected remaining 14640332764 bytes，因而在首个 RATE 前返回 RC70。问题在于后续 `failure_reason_explanation(budget-exceeded)` 只按 umbrella reason 选择“硬预算已耗尽”，没有区分实际用尽与预计不能完成；`failure_record_write` 和 `failure_summary_print` 都复用了这个错误映射。

当前代码入口：[逐阶段拒绝](/mnt/d/code/bbr/src/measure.sh:170)、[可完成性拒绝](/mnt/d/code/bbr/src/measure.sh:1798)、[分类快照](/mnt/d/code/bbr/src/diagnostics.sh:25)、[解释映射](/mnt/d/code/bbr/src/diagnostics.sh:200)、[failure writer](/mnt/d/code/bbr/src/diagnostics.sh:288)、[CLI summary](/mnt/d/code/bbr/src/diagnostics.sh:430)及 [history reader](/mnt/d/code/bbr/src/diagnostics.sh:515)。

修复后的调用链：

```text
measurement_budget_check / measurement_budget_feasibility_gate
  → failure_set(..., optional budget snapshot)
  → failure_pending_write / failure_pending_load
  → measurement_finalize_run
  → summary.tsv + failure.tsv
  → shared subtype explanation + CLI/history rendering
```

快照在原拒绝分支内生成，随 pending 文件跨子进程传回。最终接口计数更新不会把“下一样本预留不足”重新解释成“拒绝发生时预算已耗尽”。非预算失败的 pending 文件仍是原来的四字段格式；缺少新快照的旧记录按已有字段解释，不迁移或重写旧文件。

## 2. Failure classification

| `BUDGET_FAILURE_SUBTYPE` | 判据与说明 |
| --- | --- |
| `exhausted` | 拒绝快照中的实际 TX 已达到硬限额，或实际耗时已达到时间上限；对应余额为 0 |
| `insufficient-reservation` | 仍有实际余额，但下一阶段 TX/时间 reservation 会达到或越过现有安全边界；保留原严格边界比较 |
| `feasibility-rejected` | 实测容量发现后的现有 feasibility gate 拒绝所选 profile 的剩余工作量；没有将它写成实际耗尽 |
| `unknown` | 旧记录缺少足够分类证据；仅说明预算限制下安全停止，不推测实际耗尽 |

实际耗尽优先按 TX/时间快照判断。B/C 不再出现“已耗尽”。时间用尽不会伪造 TX 用尽；时间预留不足也会显示相应秒数和 cause。

`SCAN_DECISION=budget-exceeded`、`MEASUREMENT_STATE=MEASUREMENT_BUDGET_EXCEEDED`、`FAILURE_REASON=budget-exceeded` 和 RC70 保持兼容，新 subtype 提供更精确含义。没有新增 admission 分支、预算增额、profile 切换、采样缩减或成功状态。预算失败仍为 FAILURE，decision confidence 为 low/inconclusive，`CONFIRMED=0`，recommendation/confirmed knee 保持空值并在 UX 显示 none。

## 3. Structured records, CLI and compatibility

`HISTORY_SCHEMA=1`、`FAILURE_SCHEMA=1` 不变，采用可选 key/value 扩展：

| 字段 | 含义 |
| --- | --- |
| `BUDGET_FAILURE_SUBTYPE` | 上述四种分类 |
| `BUDGET_LIMIT_BYTES` / `BUDGET_USED_BYTES` / `BUDGET_REMAINING_BYTES` | 拒绝发生时的 TX 上限、已用和剩余 |
| `BUDGET_REQUIRED_RESERVATION_BYTES` | 触发拒绝的下一阶段 reservation 或 expected 剩余计划 |
| `BUDGET_LIMIT_SECONDS` / `BUDGET_USED_SECONDS` / `BUDGET_REMAINING_SECONDS` / `BUDGET_REQUIRED_RESERVATION_SECONDS` | 同一拒绝快照的时间字段 |
| `BUDGET_FEASIBILITY_REASON` | actual/next/expected 及 TX/时间维度的明确 cause |
| `BUDGET_RESERVATION_SEMANTICS` | `next-stage-reservation` 或 `expected-remaining-plan` |
| `BUDGET_PROFILE` | 拒绝时的实际 profile；缺失历史信息为 unknown |

`TEST_TX_BYTES_USED` 继续代表最终接口计量，未被快照覆盖。新回归特意让最后一次计数达到上限，验证此前发生的正余额 reservation 拒绝仍保持其原始 subtype、used/remaining，而最终计数仍真实记录后来的值。UI 使用“Budget at rejection (snapshot)”区分这两个时点。

原 feasibility gate 依赖 **expected remainder / expected duration**，不依赖完整分支 upper。修复没有更改这一规则：C 的 `BUDGET_REQUIRED_RESERVATION_BYTES` 标记为 `expected-remaining-plan`，不会把保守 upper 冒充已发送流量、物理预留或新的拒绝阈值。`CONSERVATIVE_REMAINING_UPPER_BOUND` 独立保留。

`failure.tsv` 与 summary 保存相同预算字段和建议；C 的显式重新执行建议不再被 failure writer 的通用建议覆盖。默认建议同时提及 `--max-test-gib` 和 `--max-duration`。`history` 保留原五列并追加 Budget subtype；`history latest/show`、Failure summary 使用同一解释及快照。transaction 前首样本拒绝也显示 insufficient-reservation，仍不创建测量历史或事务。

兼容检查包括：旧 P3 原错误记录只读显示正确 C；旧 v8.0.7 风格 reservation detail 推导 B；信息不足/非法数值不执行、不猜测；独立 failure writer 在 summary 尚不存在时仍可记录 unknown。正式 **v8.0.7** 脚本和旧 **P3** 脚本均已在本地成功读取新构建的 schema 1 记录，文件 hash 未变化。rollback 失败的优先 reason/RC73 规则未变。
